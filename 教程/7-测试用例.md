# 测试用例分析

本文基于当前项目源码中的测试文件、测试函数和路由注册表整理。由于当前环境缺少 `go` 命令，无法执行 `go test -cover` 生成真实语句覆盖率；本文的“接口覆盖度”采用静态源码分析口径，具体说明见“接口覆盖度”章节。

## 一、测试总体情况

| 指标 | 数量 | 说明 |
| --- | ---: | --- |
| 测试文件总数 | 40 | 39 个 Go 测试文件，1 个前端 TSX 测试文件 |
| Go 测试文件 | 39 | 文件名均为 `*_test.go` |
| 前端测试文件 | 1 | `web/default/src/components/ui/dropdown-menu.test.tsx` |
| Go `Test*` 用例 | 379 | 不含 `TestMain` |
| Go benchmark | 6 | 主要覆盖表达式计费和结算性能 |
| 前端 node:test 用例 | 2 | 另有 1 个 `describe` 分组 |
| 注册 API/Relay/视频路由 | 318 | 来自 `router/*.go` 中实际注册的 GET/POST/PUT/DELETE/PATCH 等 |

测试分布呈现明显特点：项目不是以端到端接口测试为主，而是大量保护核心业务函数、计费系统、Relay 适配、参数覆盖、流式扫描、支付防串单、任务结算和 DTO JSON 语义。

## 四、接口测试覆盖度

### 4.1 统计口径

由于不能运行真实覆盖率工具，本文采用静态口径：

- 路由总数：统计 `router/*.go` 中实际注册的 `GET/POST/PUT/DELETE/PATCH/Any/OPTIONS` 路由，排除注释掉的路由，共 318 个。
- 直接接口覆盖：测试中构造 `gin.Context` 或 `httptest` 并直接调用某个 controller handler，且该 handler 对应注册路由。
- 间接核心逻辑覆盖：未完整走路由，但测试了该接口内部使用的关键函数、服务或适配层。
- 不计入直接覆盖：只测试纯函数、模型函数、service 函数，虽然它们支撑接口行为，但未直接调用注册 handler。

## 六、测试覆盖的关键风险

| 风险点 | 测试保护 |
| --- | --- |
| 显式 0 值被 JSON `omitempty` 吞掉 | DTO 测试覆盖 OpenAI/Gemini 请求 |
| 阶梯计费和传统倍率不一致 | billingexpr、tiered_settle、text_quota 多处覆盖 |
| 预扣与最终结算不一致 | tiered_settle 和 task_billing 覆盖补扣/退款 |
| 流式响应异常结束无法归因 | stream_scanner 和 stream_status 覆盖结束原因 |
| Header/body 参数覆盖误伤请求 | override 和 api_request 测试覆盖 |
| 支付串单或错误 provider 处理订单 | payment_method_guard 和 waffo_pancake 覆盖 |
| token key 泄露 | token controller 测试覆盖列表、搜索、详情、更新脱敏 |
| 上游模型同步误增误删 | channel_upstream_update 覆盖 mapping、忽略规则和集合运算 |
| Claude/Gemini usage 统计错算 | Claude/Gemini 渠道测试和 text_quota 覆盖 |
| 配置热更新 map 合并语义错误 | setting/config 测试覆盖 map 替换与清空 |

## 七、覆盖缺口与改进建议

1. 增加 router 级集成测试：用 `router.SetRouter()` 构建完整 Gin engine，覆盖鉴权、参数绑定、中间件、handler 返回和错误码。
2. 优先补用户认证链路：注册、登录、2FA、Passkey、OAuth state/callback 是高风险入口。
3. 补支付端到端回调：Stripe/Creem/Waffo/Epay/Waffo Pancake 应覆盖签名校验、幂等、订单状态变化、余额变化。
4. 补渠道 CRUD 和 token CRUD 全流程：当前 token 只覆盖 key 安全，未覆盖新增、删除、批量 key 等完整接口。
5. 补 Relay 端到端最小闭环：OpenAI chat、responses、Claude messages、Gemini generateContent、embedding、audio、image 至少各有一条 httptest + mock upstream。
6. 补前端测试体系：当前只有一个 Node 内置测试，建议为关键 hooks、API client、表单校验、路由页面补充组件/单元测试。
7. 在 CI 中生成真实覆盖率：后端使用 `go test ./... -coverprofile=coverage.out`，前端若引入 Vitest 则输出 coverage summary。

## 八、结论

当前测试套件质量集中在“核心算法和高风险业务规则”上，尤其是阶梯计费、Relay 参数覆盖、流式扫描、任务结算和支付防串单；这些区域测试密度较高，场景也比较细。

但从接口覆盖看，直接覆盖注册 API 路由的测试很少。按静态路由总数 318 个、直接覆盖约 6 个接口计算，接口直接覆盖度约 1.9%。因此，项目目前更像是“核心逻辑单元测试较强、接口集成测试薄弱”的测试结构。
