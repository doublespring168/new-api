# 11-核心数据流

本文档基于当前项目源码整理，重点回答：系统中的核心数据从哪里进入、经过哪些模块处理、写入哪些表或缓存、再被哪些流程消费。涉及的主要源码范围包括 `main.go`、`router/`、`middleware/`、`controller/`、`relay/`、`service/`、`model/`、`setting/`、`common/`、`dto/`、`pkg/` 和前端 `web/default`、`web/classic`。

## 一、核心数据流总览

项目是一个 AI API 网关与运营管理系统，数据流可以分成 12 条主线：

| 编号 | 数据流 | 入口 | 关键处理模块 | 主要落点 |
| --- | --- | --- | --- | --- |
| 1 | 启动配置流 | `.env`、环境变量、`options` 表 | `main`、`common`、`model`、`setting` | 内存配置、数据库、Redis |
| 2 | 前端控制台流 | 浏览器访问 Web 和 `/api` | `router/web`、`controller`、`model` | 前端状态、业务表 |
| 3 | 用户登录认证流 | 注册、登录、OAuth、Passkey、2FA | `controller/user`、`oauth`、`middleware/auth` | `users`、Session、缓存 |
| 4 | API Token 流 | 控制台创建 Token、客户端携带 Token | `controller/token`、`middleware/TokenAuth`、`model/token` | `tokens`、Redis Token 缓存、Gin Context |
| 5 | Relay 请求流 | `/v1/**`、`/mj/**`、`/suno/**`、视频接口 | `middleware`、`controller/relay`、`relay`、`relay/channel` | 上游响应、消费日志、额度变更 |
| 6 | 渠道选择与重试流 | Relay 请求中的模型和分组 | `middleware/Distribute`、`service/channel_select`、`model/channel_cache` | Gin Context、渠道缓存、错误日志 |
| 7 | 计费与额度流 | Relay 请求、任务请求、充值、订阅 | `relay/helper`、`service/billing`、`model/user/token/subscription` | 用户额度、Token 额度、订阅额度、日志 |
| 8 | 异步任务流 | 视频/Suno/Midjourney/Sora/Gemini 任务 | `relay/relay_task`、`service/task_polling`、`model/task` | `tasks`、任务状态、任务结果、退款/补扣 |
| 9 | 支付充值流 | 易支付、Stripe、Creem、Waffo 等 | `controller/topup*`、`model/topup` | `top_ups`、用户额度、充值日志 |
| 10 | 订阅流 | 订阅购买、订阅订单、订阅计费 | `controller/subscription*`、`model/subscription`、`service/funding_source` | `subscription_*` 表、用户设置、额度预扣 |
| 11 | 日志与看板流 | 消费、错误、管理操作、后台聚合 | `model/log`、`model/usedata`、`pkg/perf_metrics` | `logs`、`quota_data`、`perf_metrics` |
| 12 | 管理配置与缓存流 | 管理后台修改配置/渠道/模型 | `controller/option/channel/model`、`model/option`、`setting` | `options`、`channels`、`abilities`、内存缓存 |

整体关系可以概括为：

```mermaid
flowchart TD
    Client[客户端 / 前端 / API 调用方]
    Web[前端静态资源]
    API[/api 管理接口]
    Relay[/v1 /mj /suno /video Relay]
    Auth[认证与鉴权中间件]
    Dist[渠道分发中间件]
    Controller[controller]
    RelayCore[relay 编排]
    Adapter[relay/channel 上游适配器]
    Service[service 业务服务]
    Model[model 数据访问]
    DB[(SQLite / MySQL / PostgreSQL)]
    Redis[(Redis / 内存缓存)]
    Upstream[上游 AI / 支付 / OAuth]
    Logs[日志与指标]

    Client --> Web
    Client --> API
    Client --> Relay
    API --> Auth --> Controller
    Relay --> Auth --> Dist --> Controller --> RelayCore --> Adapter --> Upstream
    Controller --> Service --> Model --> DB
    RelayCore --> Service
    Service --> Redis
    Model --> Redis
    Service --> Logs
    Model --> Logs
```

## 二、启动配置数据流

### 1. 入口数据

启动配置来自：

- `.env` 文件。
- 系统环境变量。
- 命令行参数：`--port`、`--log-dir`、`--version`、`--help`。
- 数据库 `options` 表。
- 代码默认配置：`common/constants.go`、`setting/*`、`setting/config` 注册项。

### 2. 处理链路

```text
main.main()
  -> InitResources()
      -> godotenv.Load(".env")
      -> common.InitEnv()
      -> logger.SetupLogger()
      -> ratio_setting.InitRatioSettings()
      -> service.InitHttpClient()
      -> service.InitTokenEncoders()
      -> model.InitDB()
      -> model.CheckSetup()
      -> model.InitOptionMap()
      -> model.GetPricing()
      -> model.InitLogDB()
      -> common.InitRedisClient()
      -> perfmetrics.Init()
      -> common.StartSystemMonitor()
      -> i18n.Init()
      -> oauth.LoadCustomProviders()
  -> 启动后台任务
  -> 初始化 Gin 中间件
  -> router.SetRouter()
  -> server.Run()
```

### 3. 数据落点和后续消费

| 数据 | 落点 | 后续消费 |
| --- | --- | --- |
| 端口、日志目录、调试开关 | `common` 全局变量 | Gin Server、日志系统 |
| 数据库 DSN | `model.DB`、`model.LOG_DB` | 所有 model CRUD、日志写入 |
| Redis 连接 | `common.RDB`、`common.RedisEnabled` | Token/用户缓存、限流、HybridCache |
| 系统配置默认值 | `common.OptionMap` | 控制台、运行时开关、中间件 |
| DB 中的配置项 | `options` 表 -> `OptionMap` | `setting`、`operation_setting`、`ratio_setting` |
| 模型倍率/价格 | `ratio_setting` 内存结构 | 计费、分发、价格展示 |
| i18n 语言包 | i18n 内存 bundle | 错误消息、API 响应 |
| 自定义 OAuth | OAuth provider 注册表 | 登录绑定流程 |

### 4. 一致性点

- `model.InitOptionMap()` 必须在 `model.InitDB()` 之后，因为配置项来自数据库。
- `model.InitLogDB()` 可复用主库，也可由 `LOG_SQL_DSN` 指向独立日志库。
- Redis 未配置时系统降级运行；Redis 配置错误时启动失败。
- `model.SyncOptions()` 会周期性从数据库刷新配置到内存。
- `model.SyncChannelCache()` 会周期性从数据库刷新渠道能力缓存。

## 三、前端控制台数据流

### 1. 生产模式前端数据流

```text
web/default 或 web/classic 源码
  -> Dockerfile 中 bun run build
  -> 生成 dist
  -> Go 编译阶段复制 dist
  -> main.go go:embed
  -> router/web-router.go static.Serve
  -> 浏览器加载前端
  -> 前端请求 /api
```

生产运行时没有独立前端服务，前端页面由 Go 后端托管。

### 2. 控制台 API 数据流

典型链路：

```text
浏览器
  -> /api/**
  -> GlobalAPIRateLimit
  -> UserAuth / AdminAuth / RootAuth
  -> controller
  -> service/model
  -> DB/Redis
  -> common.ApiSuccess / ApiError
  -> 前端 React Query / 页面状态
```

### 3. 控制台主要读写对象

| 控制台功能 | 读取 | 写入 |
| --- | --- | --- |
| 用户中心 | `users`、Session | `users.setting`、`users.access_token` |
| Token 管理 | `tokens` | `tokens`、Redis Token 缓存失效 |
| 渠道管理 | `channels`、`abilities`、`vendors`、`models` | 渠道配置、能力表、渠道缓存 |
| 系统配置 | `options`、`OptionMap` | `options`、内存配置 |
| 日志查询 | `logs`、`quota_data` | 不写，查询过滤 |
| 订阅/充值 | `top_ups`、`subscription_*` | 订单、用户额度、订阅实例 |
| 任务列表 | `tasks`、`midjourneys` | 任务状态查询和管理操作 |

## 四、用户登录与身份认证数据流

### 1. 注册数据流

```text
POST /api/user/register
  -> CriticalRateLimit
  -> TurnstileCheck
  -> controller.Register
      -> 校验注册开关
      -> 校验输入
      -> 可选邮箱验证码校验
      -> model.CheckUserExistOrDeleted
      -> 邀请码解析 model.GetUserIdByAffCode
      -> model.User.Insert
      -> 可选生成默认 Token
  -> users 表
  -> tokens 表
```

核心写入：

- `users.username`
- `users.password`
- `users.email`
- `users.inviter_id`
- `users.role`
- `users.quota`
- 可选 `tokens` 初始令牌。

### 2. 登录数据流

```text
POST /api/user/login
  -> CriticalRateLimit
  -> TurnstileCheck
  -> controller.Login
      -> model.User.ValidateAndFill
      -> 检查 2FA
      -> setupLogin
          -> model.UpdateUserLastLoginAt
          -> sessions.Default(c).Set(...)
  -> Cookie Session
```

Session 中保存：

- `id`
- `username`
- `role`
- `status`
- `group`

后续管理 API 通过 `UserAuth`、`AdminAuth`、`RootAuth` 读取 Session 并写入 Gin Context。

### 3. 管理 API 鉴权数据流

```text
请求 /api/**
  -> sessions.Sessions
  -> UserAuth/AdminAuth/RootAuth
      -> 优先读 Session
      -> 无 Session 时尝试 Authorization access token
      -> 校验 New-Api-User 头与用户 ID 一致
      -> 校验状态和角色
      -> 写入 Gin Context
  -> controller
```

Gin Context 写入字段：

- `id`
- `username`
- `role`
- `group`
- `user_group`
- `use_access_token`

### 4. OAuth、Passkey、2FA 的位置

这些认证方式最终都会汇入同一个身份状态：

- OAuth 登录绑定或创建用户后写入 `users`、`user_oauth_bindings`。
- Passkey 写入 `passkey_credentials`。
- 2FA 写入 `two_fas`、`two_fa_backup_codes`。
- 登录成功后仍通过 Session 承载控制台登录态。

## 五、API Token 数据流

### 1. Token 创建流

```text
POST /api/token/
  -> UserAuth
  -> controller.AddToken
      -> 校验名称、额度、模型限制
      -> model.CountUserTokens
      -> common.GenerateKey
      -> model.Token 创建
  -> tokens 表
```

Token 主要字段：

- `user_id`
- `key`
- `status`
- `name`
- `remain_quota`
- `unlimited_quota`
- `model_limits_enabled`
- `model_limits`
- `group`
- `cross_group_retry`
- `allow_ips`
- `expired_time`

### 2. Token 认证流

```text
客户端请求 /v1/**
  -> middleware.TokenAuth
      -> 从 Authorization/x-api-key/query/mj-api-secret 等位置解析 key
      -> model.ValidateUserToken
      -> model.GetTokenByKey
      -> 读 Redis token 缓存，未命中读 DB
      -> 校验状态、过期、额度、IP 白名单
      -> 读取用户缓存 model.GetUserCache / GetUserQuota / GetUserGroup / GetUserSetting
      -> 计算 Token 使用分组
      -> 写入 Gin Context
  -> ModelRequestRateLimit
  -> Distribute
```

### 3. Token 缓存流

```text
GetTokenByKey(fromDB=false)
  -> Redis token:{hmacKey}
  -> 未命中读 tokens 表
  -> 异步 cacheSetToken
```

Token 额度变化：

- `model.DecreaseTokenQuota`
- `model.IncreaseTokenQuota`
- Redis 启用时同步更新 Redis hash。
- Redis 未启用时直接更新 DB 状态。

### 4. Token 数据被谁消费

| 消费方 | 使用字段 |
| --- | --- |
| `TokenAuth` | key、状态、过期、额度、模型限制、分组、IP |
| `Distribute` | 模型限制、使用分组、指定渠道 |
| `ModelRequestRateLimit` | 用户 ID、Token 分组 |
| `BillingSession` | token_id、token_key、unlimited_quota |
| 日志系统 | token_id、token_name |
| 前端控制台 | Token 列表、用量、密钥展示 |

## 六、Relay 请求核心数据流

这是项目最重要的数据流。

### 1. 标准文本/图片/音频/Embedding 请求流

```text
客户端请求 /v1/chat/completions 或其他兼容接口
  -> CORS
  -> DecompressRequestMiddleware
  -> BodyStorageCleanup
  -> StatsMiddleware
  -> RouteTag(relay)
  -> SystemPerformanceCheck
  -> TokenAuth
  -> ModelRequestRateLimit
  -> Distribute
      -> 解析 model/group
      -> 检查 Token 模型限制
      -> 选择分组
      -> 选择渠道
      -> SetupContextForSelectedChannel
  -> controller.Relay
      -> helper.GetAndValidateRequest
      -> relaycommon.GenRelayInfo
      -> 敏感词检查
      -> service.EstimateRequestToken
      -> helper.ModelPriceHelper
      -> service.PreConsumeBilling
      -> relay handler
          -> relay.GetAdaptor
          -> adaptor.Convert...
          -> adaptor.DoRequest
          -> adaptor.DoResponse
      -> service.SettleBilling
      -> model.RecordConsumeLog
      -> perfmetrics.RecordRelaySample
  -> 返回客户端
```

### 2. RelayInfo 是核心中间数据结构

`relay/common.RelayInfo` 汇总了整个请求生命周期中的核心数据：

| 数据 | 来源 | 用途 |
| --- | --- | --- |
| 用户 ID、Token ID、Token key | `TokenAuth` context | 计费、日志、权限 |
| 原始模型、上游模型 | 请求体、模型映射 | 计费、渠道适配 |
| 分组、用户组、Token 组 | Token 和用户设置 | 渠道选择、倍率 |
| 渠道 ID、类型、BaseURL、Key | `Distribute` context | 上游请求 |
| API 类型、RelayMode、格式 | 路由和请求 | 选择 handler/adaptor |
| 价格数据 PriceData | `ModelPriceHelper` | 预扣费和结算 |
| BillingSession | `PreConsumeBilling` | 结算/退款 |
| 请求开始时间 | `Distribute` | 日志和性能指标 |
| 用户设置 | 用户缓存 | 通知、IP 日志、计费偏好 |

### 3. 上游适配数据流

```text
relay handler
  -> relay.GetAdaptor(apiType)
  -> adaptor.Init(info)
  -> adaptor.GetRequestURL(info)
  -> adaptor.SetupRequestHeader(...)
  -> adaptor.ConvertOpenAIRequest / ConvertClaudeRequest / ConvertGeminiRequest ...
  -> relay/channel/api_request.DoRequest
  -> 上游 Provider
  -> adaptor.DoResponse
  -> dto.Usage / TaskInfo / 错误
```

每个 Provider 适配器负责：

- URL 拼接。
- Header 设置。
- 模型名映射。
- 请求体格式转换。
- 流式/非流式响应解析。
- usage 提取。
- 错误格式归一。

### 4. 请求体复用数据流

Relay 请求可能被多个阶段读取，因此项目使用 body storage：

```text
DecompressRequestMiddleware
  -> common.GetBodyStorage / UnmarshalBodyReusable
  -> Distribute 解析 model
  -> controller.Relay 校验 request
  -> 重试时重置 c.Request.Body
  -> BodyStorageCleanup 清理
```

这个流保证了：

- 请求体可重复读取。
- 重试时可以重新发送同一请求体。
- 大请求结束后临时资源被清理。

## 七、渠道选择、缓存与重试数据流

### 1. 渠道缓存构建流

```text
main 启动
  -> model.InitChannelCache
      -> 读取 channels 表
      -> 读取 abilities 表
      -> 过滤启用渠道
      -> 按 group/model 构建 channel id 列表
      -> 按 priority 排序
      -> 处理多 key 渠道轮询索引
      -> 写入内存:
          group2model2channels
          channelsIDM
  -> model.SyncChannelCache 定时刷新
```

缓存结构：

```text
group2model2channels[group][model] = []channelId
channelsIDM[channelId] = *Channel
```

### 2. 请求分发流

```text
Distribute
  -> getModelRequest
  -> 检查 Token 模型限制
  -> usingGroup = Token/用户分组
  -> 若 Playground 可覆盖 group
  -> 若命中渠道亲和性，优先使用偏好渠道
  -> 否则 service.CacheGetRandomSatisfiedChannel
  -> middleware.SetupContextForSelectedChannel
```

### 3. auto 分组数据流

```text
TokenGroup = auto
  -> setting.GetAutoGroups()
  -> service.GetUserAutoGroup(userGroup)
  -> 按 auto group 顺序尝试
  -> 每个 group 内按 priority/retry 选择渠道
  -> 写入 ContextKeyAutoGroup
```

如果启用跨分组重试：

- 当前分组用尽重试优先级后切换到下一个 auto 分组。
- Context 中记录当前 group index 和 retry index。

### 4. 权重与优先级选择

`model.GetRandomSatisfiedChannel` 的选择规则：

1. 优先精确模型名。
2. 无匹配时使用归一化模型名。
3. 按 priority 从高到低分层。
4. 同一 priority 内按 weight 随机。
5. retry 次数决定使用第几个 priority 层。

### 5. 渠道错误与自动禁用流

```text
上游请求失败
  -> controller.Relay 得到 NewAPIError
  -> processChannelError
      -> 记录错误日志
      -> service.ShouldDisableChannel
      -> service.DisableChannel
      -> model.CacheUpdateChannelStatus
  -> shouldRetry 判断是否重试
```

错误数据流向：

- `logs` 表的错误日志。
- `channels.status`。
- 内存渠道缓存。
- 性能指标 `perf_metrics`。

## 八、计费与额度数据流

计费数据流横跨 Relay、任务、充值和订阅，是项目最复杂的状态流。

### 1. 价格计算流

```text
请求模型 + 分组 + Token meta
  -> service.EstimateRequestToken
  -> helper.ModelPriceHelper / ModelPriceHelperPerCall
      -> ratio_setting.GetModelRatio / GetModelPrice
      -> ratio_setting.GetGroupRatio
      -> GroupGroupRatio 特殊倍率
      -> 可选 billingexpr 表达式计费
      -> 得到 PriceData
```

`PriceData` 包含：

- 预扣额度。
- 模型倍率或模型价格。
- 分组倍率。
- 是否免费模型。
- 是否按次计费。
- 阶梯计费快照。
- 图片/音频/任务的额外倍率。

### 2. 预扣费流

```text
service.PreConsumeBilling
  -> service.NewBillingSession
      -> 根据用户 BillingPreference 选择资金来源
          -> wallet
          -> subscription
      -> BillingSession.preConsume
          -> 判断信任额度旁路
          -> PreConsumeTokenQuota
          -> FundingSource.PreConsume
              -> WalletFunding: model.DecreaseUserQuota
              -> SubscriptionFunding: model.PreConsumeUserSubscription
      -> relayInfo.Billing = session
```

资金来源：

| 来源 | 写入位置 | 说明 |
| --- | --- | --- |
| 钱包余额 | `users.quota` | 用户通用额度 |
| API Token | `tokens.remain_quota` | Token 级额度限制 |
| 订阅额度 | `user_subscriptions`、`subscription_pre_consume_records` | 订阅套餐额度 |

### 3. 上游成功后的结算流

```text
adaptor.DoResponse 提取 usage
  -> service.PostConsumeQuota / PostAudioConsumeQuota / PostWssConsumeQuota
  -> service.SettleBilling(actualQuota)
      -> BillingSession.Settle
          -> funding.Settle(delta)
          -> token quota 增减 delta
      -> 额度提醒通知
  -> model.UpdateUserUsedQuotaAndRequestCount
  -> model.UpdateChannelUsedQuota
  -> model.RecordConsumeLog
```

`delta = actualQuota - preConsumedQuota`：

- `delta > 0`：补扣。
- `delta < 0`：退还。
- `delta = 0`：无需调整。

### 4. 请求失败后的退款流

```text
controller.Relay defer
  -> newAPIError != nil
  -> relayInfo.Billing.Refund(c)
      -> funding.Refund()
      -> model.IncreaseTokenQuota
  -> service.ChargeViolationFeeIfNeeded
```

退款是异步执行，并且 `BillingSession` 使用状态字段保证幂等：

- `settled`
- `refunded`
- `fundingSettled`

### 5. 额度数据被谁消费

| 数据 | 消费方 |
| --- | --- |
| `users.quota` | Token 创建、Relay 预扣、控制台展示、充值 |
| `users.used_quota` | 管理统计、用户用量 |
| `tokens.remain_quota` | TokenAuth、预扣费、Token 用量查询 |
| `tokens.used_quota` | Token 用量展示 |
| `channels.used_quota` | 渠道统计、管理后台 |
| `logs.quota` | 用户日志、管理日志、用量分析 |
| `quota_data` | 数据看板 |
| `user_subscriptions.amount_used` | 订阅用量和续期重置 |

## 九、异步任务数据流

异步任务覆盖视频、Suno、Midjourney、Sora、Gemini/Vertex 等任务型上游。

### 1. 任务提交流

```text
客户端提交任务
  -> TokenAuth
  -> Distribute
  -> controller.RelayTask / relay.RelayTaskSubmit
      -> info.InitChannelMeta
      -> 确定 platform/adaptor
      -> adaptor.ValidateRequestAndSetAction
      -> 确定模型名
      -> helper.ModelMappedHelper
      -> 生成 PublicTaskID
      -> helper.ModelPriceHelperPerCall
      -> adaptor.EstimateBilling
      -> service.PreConsumeBilling
      -> adaptor.BuildRequestBody
      -> adaptor.DoRequest
      -> adaptor.DoResponse
      -> adaptor.AdjustBillingOnSubmit
      -> 创建/更新 tasks
  -> 返回 task_id
```

任务提交时关键数据：

- `task_id`：对客户端暴露的任务 ID。
- `upstream_task_id`：上游任务 ID，保存在 `tasks.private_data` 或相关字段中。
- `platform`：任务平台。
- `channel_id`：实际使用渠道。
- `quota`：预扣额度。
- `private_data`：计费上下文、上游数据、结果 URL 等。

### 2. 任务查询流

```text
客户端查询 /v1/video/generations/{task_id} 或 Suno 查询
  -> TokenAuth 或 TokenOrUserAuth
  -> relay.RelayTaskFetch
      -> model.GetByTaskId / GetByTaskIds
      -> 可选 tryRealtimeFetch
      -> adaptor.ConvertToOpenAIVideo
      -> 返回 TaskDto 或 OpenAI Video 格式
```

查询优先读取本地 `tasks` 表；Gemini/Vertex 视频任务支持在查询时实时拉上游状态并更新本地任务。

### 3. 后台轮询流

```text
main 注入 service.GetTaskAdaptorFunc = relay.GetTaskAdaptor
  -> controller.UpdateTaskBulk / service.TaskPollingLoop
      -> model.GetAllUnFinishSyncTasks
      -> 按 platform 分组
      -> 按 channel_id 聚合 upstream_task_id
      -> DispatchPlatformUpdate
          -> Suno: UpdateSunoTasks
          -> 视频: UpdateVideoTasks
      -> adaptor.FetchTask
      -> adaptor.ParseTaskResult
      -> 更新 tasks 状态/进度/结果
      -> 成功: settleTaskBillingOnComplete
      -> 失败/超时: RefundTaskQuota
```

### 4. 任务状态流

```text
SUBMITTED / IN_PROGRESS
  -> SUCCESS
  -> FAILURE
```

状态变化带来的数据更新：

| 状态 | 数据动作 |
| --- | --- |
| 提交成功 | 写入任务、预扣额度 |
| 进行中 | 更新 progress、上游数据 |
| 成功 | 写入结果 URL/data，可能按实际 token 补扣/退还 |
| 失败 | 写 fail_reason，退还预扣额度 |
| 超时 | 标记失败，非遗留任务退款 |

### 5. 任务计费流

任务计费与普通 Relay 的差异：

- 提交时通常 `ForcePreConsume=true`，不允许信任额度旁路。
- 按次计费任务成功后可能不再差额结算。
- 对于 token 型任务，终态时可根据 `TotalTokens` 重算。
- 适配器可通过 `AdjustBillingOnSubmit` 和 `AdjustBillingOnComplete` 调整额度。

## 十、支付充值数据流

### 1. 易支付充值流

```text
POST /api/user/pay
  -> UserAuth
  -> CriticalRateLimit
  -> controller.RequestEpay
      -> 校验金额和支付方式
      -> model.GetUserGroup
      -> getPayMoney
      -> epay.Client.Purchase
      -> model.TopUp.Insert(status=pending)
  -> 返回支付参数

支付网关回调 /api/user/epay/notify
  -> controller.EpayNotify
      -> 验签
      -> LockOrder(trade_no)
      -> model.GetTopUpByTradeNo
      -> 校验 provider/method/status
      -> topUp.Status = success
      -> model.IncreaseUserQuota
      -> model.RecordTopupLog
  -> 返回 success
```

幂等点：

- `trade_no` 订单号。
- `LockOrder` 本进程锁。
- 只处理 `TopUpStatusPending` 订单。

### 2. Stripe 充值流

```text
POST /api/user/stripe/pay
  -> UserAuth
  -> controller.RequestStripePay
      -> 校验金额、支付方式、重定向 URL
      -> genStripeLink
      -> model.TopUp.Insert(status=pending)
  -> 返回 checkout url

POST /api/stripe/webhook
  -> StripeWebhook
      -> 读取 body
      -> webhook.ConstructEventWithOptions 验签
      -> checkout.session.completed / async_payment_succeeded
      -> fulfillOrder
          -> 先尝试 model.CompleteSubscriptionOrder
          -> 若非订阅订单则 model.Recharge
      -> checkout.session.expired / async_payment_failed 更新订单状态
```

Stripe 回调同时服务：

- 普通充值订单。
- 订阅订单。

### 3. 充值数据落点

| 表 | 作用 |
| --- | --- |
| `top_ups` | 保存充值订单、金额、支付网关、状态 |
| `users` | 支付成功后增加用户额度 |
| `logs` | 记录充值日志 |

## 十一、订阅数据流

### 1. 订阅计划管理流

```text
Admin API
  -> AdminAuth
  -> controller.AdminCreateSubscriptionPlan / AdminUpdateSubscriptionPlan
      -> 校验套餐标题、价格、周期、升级分组、重置周期
      -> model.DB.Create / Save
      -> model.InvalidateSubscriptionPlanCache
  -> subscription_plans
```

### 2. 用户订阅购买流

余额购买：

```text
POST /api/subscription/balance/pay
  -> UserAuth
  -> controller.SubscriptionRequestBalancePay
  -> model.PurchaseSubscriptionWithBalance
      -> 扣用户余额
      -> 创建 UserSubscription
      -> 记录订单/日志
```

在线支付购买：

```text
创建 subscription_order
  -> 跳转支付
  -> 支付 webhook
  -> model.CompleteSubscriptionOrder
      -> 更新订单成功
      -> 创建或续期 user_subscription
```

### 3. 订阅计费流

```text
用户设置 BillingPreference
  -> Relay PreConsumeBilling
      -> SubscriptionFunding
      -> model.PreConsumeUserSubscription
          -> 选择可用订阅
          -> 写 subscription_pre_consume_records
          -> 增加 user_subscriptions.amount_used
```

订阅计费的关键点：

### 4. 订阅重置流

```text

      -> 重置用户订阅额度使用量
```

## 十六、核心数据流之间的依赖关系

### 1. Relay 依赖 Token、渠道、配置、计费

```text
TokenAuth 提供用户和 Token
Distribute 提供渠道和模型
OptionMap/ratio_setting 提供计费倍率
BillingSession 修改额度
Log/PerfMetrics 记录结果
```

任一数据缺失都会影响 Relay：

- Token 无效：请求被拒绝。
- 渠道不可用：返回模型/渠道不可用。
- 计费配置错误：价格计算失败。
- 额度不足：预扣失败。
- 上游失败：可能重试、禁用渠道、记录错误日志。

### 2. 任务流依赖 Relay 的分发和计费

任务提交不是独立系统，而是复用：

- TokenAuth。
- Distribute。
- RelayInfo。
- Provider adaptor。
- BillingSession。

任务自己的差异在于：

- 提交后本地保存任务。
- 后台轮询上游状态。
- 终态时补扣/退款。

### 3. 支付和订阅反向补充计费资金来源

```text
支付成功
  -> 增加 users.quota 或创建 user_subscriptions
  -> Relay 预扣费可用额度增加
```

支付流和 Relay 流通过以下数据连接：

- `users.quota`
- `user_subscriptions`
- `subscription_pre_consume_records`
- `users.setting.billing_preference`

### 4. 配置流影响几乎所有运行时

`options` 表和 `OptionMap` 会影响：

- 登录注册开关。
- Turnstile。
- 支付方式。
- 模型倍率和价格。
- 分组倍率。
- 自动重试状态码。
- 渠道自动禁用。
- 敏感词。
- 任务开关。
- 前端展示配置。

因此配置更新不是普通 CRUD，而是“DB 持久化 + 内存热更新 + 多节点定时同步”的数据流。

## 十七、关键一致性和幂等设计

| 场景 | 设计 |
| --- | --- |
| 请求失败退款 | `BillingSession` 用 `settled/refunded/fundingSettled` 控制幂等 |
| 支付回调重复 | `LockOrder` + 订单状态只处理 pending |
| 订阅预扣 | `subscription_pre_consume_records` 记录预扣 |
| Token/User 缓存 | Redis 命中优先，DB 读取后异步回填 |
| 渠道缓存 | 定时全量刷新，禁用时局部更新 |
| 任务状态更新 | 轮询时使用状态判断和 CAS 更新，避免覆盖终态 |
| 日志库 | 可独立 `LOG_SQL_DSN`，避免主业务库和日志库强绑定 |
| 多节点配置同步 | `SyncOptions` 周期性从 DB 刷新 |

## 十八、排查问题时的数据流入口

| 问题 | 优先查看的数据流 |
| --- | --- |
| API key 无法调用 | Token 认证流、Token 缓存、用户状态 |
| 找不到模型或渠道 | 渠道缓存流、`channels`、`abilities`、分组配置 |
| 扣费异常 | 计费与额度流、`logs.other`、`users.quota`、`tokens.remain_quota`、订阅预扣记录 |
| 请求失败但额度没退 | `BillingSession.Refund`、错误是否已结算、任务是否终态 |
| 任务一直进行中 | 异步任务轮询流、`tasks.upstream_task_id`、渠道 task adaptor |
| 支付成功未到账 | 支付回调流、`top_ups.status`、webhook 验签、订单号 |
| 配置修改不生效 | 配置热更新流、`options`、`OptionMap`、多节点同步间隔 |
| 日志缺失 | `LogConsumeEnabled`、`ERROR_LOG_ENABLED`、`LOG_SQL_DSN` |
| 多节点行为不一致 | `SESSION_SECRET`、`CRYPTO_SECRET`、Redis、`NODE_TYPE`、`SyncOptions` |

## 十九、总结

项目的核心数据流可以浓缩为四个闭环：

1. 请求闭环  
   客户端请求进入路由和中间件，经过认证、限流、分发、上游适配，最终返回响应。

2. 计费闭环  
   请求开始前估算并预扣，成功后按 usage 结算，失败时退款，所有动作同步影响用户、Token、订阅和日志。

3. 运营闭环  
   管理后台修改配置、渠道、模型、价格、支付和订阅，写入数据库后同步到内存，随后影响 Relay 实时行为。

4. 观测闭环  
   消费、错误、任务、支付和性能数据写入日志与指标表，再被控制台、看板和管理接口查询使用。

这四个闭环通过 `Gin Context + RelayInfo + GORM Model + Redis/内存缓存 + options 热更新` 串联，构成当前项目的核心运行机制。
