# 9-部署机制

本文档基于当前项目源码与部署配置整理，重点分析项目采用的快速部署机制、各服务职能、前后依赖关系、启动流程和部署注意事项。涉及的主要文件包括：`Dockerfile`、`Dockerfile.dev`、`docker-compose.yml`、`docker-compose.dev.yml`、`.env.example`、`makefile`、`new-api.service`、`main.go`、`model/main.go`、`common/init.go`、`common/redis.go`、`README.zh_CN.md`、`docs/installation/BT.md` 和 `.github/workflows/`。

## 一、快速部署机制概览

当前项目的快速部署机制以 **Docker 镜像 + Docker Compose 编排** 为主。

生产部署推荐路径：

```text
拉取 calciumion/new-api:latest
  -> docker-compose.yml 启动 new-api + Redis + PostgreSQL
  -> new-api 容器连接数据库和 Redis
  -> 应用启动时自动迁移数据库、初始化配置、加载前端静态资源
  -> 对外暴露 3000 端口
```

项目还支持几种补充部署方式：

| 部署方式 | 适用场景 | 机制 |
| --- | --- | --- |
| Docker Compose | 推荐生产/测试快速部署 | 一次启动应用、Redis、PostgreSQL，可切换 MySQL |
| Docker 单容器 | 小规模或已有外部数据库/Redis | 单独运行 `calciumion/new-api:latest`，可默认 SQLite |
| 宝塔面板 | 面板化运维 | 基于 Docker 应用商店或手写 compose |
| 开发 compose | 本地前后端联调 | 后端容器 + Redis + PostgreSQL，前端本地 Bun dev server |
| 本机二进制 + systemd | 不使用 Docker 的服务器部署 | 构建二进制，systemd 守护进程 |
| GitHub Actions 发布 | 官方镜像/Release 产物构建 | 多架构 Docker 镜像、Linux/macOS/Windows 二进制 |

核心设计是：**前端在构建阶段被打包进 Go 后端二进制，运行时只需要启动一个后端进程即可同时提供 API、Relay 和前端页面。**

## 二、生产 Docker 镜像构建机制

源码位置：`Dockerfile`

生产镜像采用多阶段构建：

| 阶段 | 基础镜像 | 职能 |
| --- | --- | --- |
| `builder` | `oven/bun:1` | 构建 `web/default` 默认前端主题 |
| `builder-classic` | `oven/bun:1` | 构建 `web/classic` 经典前端主题 |
| `builder2` | `golang:1.26.1-alpine` | 下载 Go 依赖，复制前端 dist，编译 Go 二进制 |
| 最终运行阶段 | `debian:bookworm-slim` | 安装 CA 证书、时区、运行 `/new-api` |

### 1. 默认前端构建

构建流程：

```text
COPY web/default/package.json
COPY web/default/bun.lock
RUN bun install
COPY ./web/default .
COPY ./VERSION .
RUN DISABLE_ESLINT_PLUGIN='true' VITE_REACT_APP_VERSION=$(cat VERSION) bun run build
```

作用：

- 使用 Bun 安装默认前端依赖。
- 注入版本号 `VITE_REACT_APP_VERSION`。
- 生成 `web/default/dist`。

### 2. 经典前端构建

构建流程与默认前端类似：

```text
COPY web/classic/package.json
COPY web/classic/bun.lock
RUN bun install
COPY ./web/classic .
COPY ./VERSION .
RUN VITE_REACT_APP_VERSION=$(cat VERSION) bun run build
```

作用：

- 构建 classic 主题。
- 生成 `web/classic/dist`。

### 3. 后端编译与前端嵌入

Go 构建阶段会把两个前端构建产物复制到源码目录：

```text
COPY --from=builder /build/dist ./web/default/dist
COPY --from=builder-classic /build/dist ./web/classic/dist
RUN go build -ldflags "-s -w -X 'github.com/QuantumNous/new-api/common.Version=$(cat VERSION)'" -o new-api
```

对应 `main.go` 中使用 `go:embed` 嵌入前端资源：

```text
//go:embed web/default/dist
//go:embed web/default/dist/index.html
//go:embed web/classic/dist
//go:embed web/classic/dist/index.html
```

这意味着生产运行时不需要额外的 Node/Bun 服务，也不需要 Nginx 单独托管前端。Go 进程会同时负责：

- 后端管理 API。
- OpenAI/Claude/Gemini 等兼容 Relay API。
- 前端静态资源服务。
- SPA fallback。

### 4. 最终运行镜像

最终镜像只保留运行所需内容：

- `/new-api` 二进制。
- `LICENSE`、`NOTICE`、`THIRD-PARTY-LICENSES.md`。
- CA 证书和时区数据。
- 工作目录 `/data`。
- 暴露端口 `3000`。
- 启动命令 `ENTRYPOINT ["/new-api"]`。

容器默认工作目录为 `/data`，因此未配置外部数据库时，SQLite 数据库会默认落在 `/data` 下。

## 三、生产 Docker Compose 服务职能

源码位置：`docker-compose.yml`

生产 compose 默认包含 3 个服务：

```text
new-api
  -> redis
  -> postgres
```

同时保留了可选 `mysql` 服务配置，用户可以注释 PostgreSQL、启用 MySQL。

### 1. `new-api` 服务

职能：

- 运行主应用容器 `calciumion/new-api:latest`。
- 对外暴露 `3000:3000`。
- 提供前端页面、管理 API、Relay API、视频接口、任务查询等所有应用能力。
- 启动时连接数据库和 Redis。
- 启动时执行数据库迁移。
- 初始化系统配置、模型价格、缓存、i18n、自定义 OAuth、后台任务。
- 承载访问日志、错误日志、批量更新、渠道检测、任务轮询等运行时能力。

关键配置：

| 配置 | 作用 |
| --- | --- |
| `image: calciumion/new-api:latest` | 使用官方生产镜像 |
| `command: --log-dir /app/logs` | 指定日志目录 |
| `ports: "3000:3000"` | 暴露 Web/API 入口 |
| `volumes: ./data:/data` | 持久化 SQLite、临时数据、运行数据 |
| `volumes: ./logs:/app/logs` | 持久化日志 |
| `SQL_DSN=postgresql://root:123456@postgres:5432/new-api` | 连接 compose 内 PostgreSQL |
| `REDIS_CONN_STRING=redis://:123456@redis:6379` | 连接 compose 内 Redis |
| `TZ=Asia/Shanghai` | 设置容器时区 |
| `ERROR_LOG_ENABLED=true` | 启用错误日志记录 |
| `BATCH_UPDATE_ENABLED=true` | 启用批量更新 |
| `NODE_NAME=new-api-node-1` | 设置节点名称，便于审计日志识别 |

健康检查：

```text
wget -q -O - http://localhost:3000/api/status | grep -o '"success":\s*true'
```

该检查用于确认 HTTP 服务已启动且 `/api/status` 正常返回。

### 2. `redis` 服务

职能：

- 提供缓存能力。
- 支撑分布式限流。
- 缓存用户、Token、渠道、订阅、亲和性等数据。
- 在多实例部署中提供共享状态。
- 配合批量更新和缓存同步减少数据库压力。

关键配置：

| 配置 | 作用 |
| --- | --- |
| `image: redis:latest` | Redis 服务镜像 |
| `command: ["redis-server", "--requirepass", "123456"]` | 启动 Redis 并设置密码 |
| `networks: new-api-network` | 与应用容器在同一网络内通信 |

应用侧通过 `REDIS_CONN_STRING` 连接：

```text
redis://:123456@redis:6379
```

如果不设置 `REDIS_CONN_STRING`，源码中的 `common.InitRedisClient()` 会关闭 Redis 模式，应用仍可启动，但会失去 Redis 共享缓存和分布式能力。

### 3. `postgres` 服务

职能：

- 作为默认生产数据库。
- 保存用户、Token、渠道、日志、任务、兑换码、订阅、模型、配置等核心业务数据。
- 由应用启动时通过 GORM 自动迁移表结构。

关键配置：

| 配置 | 作用 |
| --- | --- |
| `image: postgres:15` | PostgreSQL 数据库 |
| `POSTGRES_USER=root` | 数据库用户 |
| `POSTGRES_PASSWORD=123456` | 数据库密码 |
| `POSTGRES_DB=new-api` | 默认数据库 |
| `volumes: pg_data:/var/lib/postgresql/data` | 持久化数据库文件 |

### 4. 可选 `mysql` 服务

compose 中保留了注释掉的 MySQL 服务：

```text
image: mysql:8.2
MYSQL_ROOT_PASSWORD=123456
MYSQL_DATABASE=new-api
```

启用 MySQL 时需要：

- 注释 `postgres` 服务。
- 注释 PostgreSQL 的 `SQL_DSN`。
- 取消 MySQL `SQL_DSN` 注释：

```text
SQL_DSN=root:123456@tcp(mysql:3306)/new-api
```

- 在 `depends_on` 中启用 `mysql`。
- 在 volumes 中启用 `mysql_data`。

源码中 `model.chooseDB()` 会根据 `SQL_DSN` 前缀判断数据库类型：

| DSN 类型 | 数据库 |
| --- | --- |
| `postgres://...` 或 `postgresql://...` | PostgreSQL |
| `local...` | SQLite |
| 其他非空 DSN | MySQL |
| 未设置 `SQL_DSN` | SQLite |

## 四、服务间前后依赖关系

### 1. compose 编排依赖

生产 compose 中：

```yaml
new-api:
  depends_on:
    - redis
    - postgres
```

含义：

- Docker Compose 会先创建并启动 Redis 和 PostgreSQL 容器。
- 再启动 `new-api` 容器。
- 生产 compose 的 `depends_on` 只保证启动顺序，不等同于数据库已完全 ready。
- `new-api` 启动后会立即尝试连接数据库和 Redis；如果依赖服务还未就绪，可能导致应用启动失败并依赖 `restart: always` 自动重启恢复。

开发 compose 中：

```yaml
new-api:
  depends_on:
    redis:
      condition: service_started
    postgres:
      condition: service_healthy
```

开发配置对 PostgreSQL 设置了 healthcheck，后端会等待 PostgreSQL 健康后再启动，启动稳定性比生产 compose 更强。

### 2. 应用内部启动依赖

`main.go` 中的启动流程如下：

```text
InitResources()
  -> godotenv.Load(".env")
  -> common.InitEnv()
  -> logger.SetupLogger()
  -> ratio_setting.InitRatioSettings()
  -> service.InitHttpClient()
  -> service.InitTokenEncoders()
  -> model.InitDB()
  -> model.CheckSetup()
  -> model.InitOptionMap()
  -> common.CleanupOldCacheFiles()
  -> model.GetPricing()
  -> model.InitLogDB()
  -> common.InitRedisClient()
  -> perfmetrics.Init()
  -> common.StartSystemMonitor()
  -> i18n.Init()
  -> i18n.SetUserLangLoader(model.GetUserLanguage)
  -> oauth.LoadCustomProviders()
```

之后进入运行期任务初始化：

```text
如果 Redis 启用，则强制开启内存缓存兼容模式
如果内存缓存启用：
  -> model.InitChannelCache()
  -> go model.SyncChannelCache()
go model.SyncOptions()
go model.UpdateQuotaData()
可选 go controller.AutomaticallyUpdateChannels()
go controller.AutomaticallyTestChannels()
service.StartCodexCredentialAutoRefreshTask()
service.StartSubscriptionQuotaResetTask()
controller.StartChannelUpstreamModelUpdateTask()
主节点且 UPDATE_TASK=true 时启动异步任务轮询
BATCH_UPDATE_ENABLED=true 时启动批量更新器
ENABLE_PPROF=true 时启动 pprof 和监控
初始化 Gin、Session、中间件、路由
server.Run(":PORT")
```

关键依赖顺序：

| 阶段 | 依赖 | 原因 |
| --- | --- | --- |
| `common.InitEnv()` | `.env` / 环境变量 | 先读取端口、数据库、Redis、密钥、限流等配置 |
| `model.InitDB()` | 数据库可连接 | 后续配置、用户、渠道、迁移都依赖 DB |
| `model.CheckSetup()` | DB 已初始化 | 判断系统是否完成初始化 |
| `model.InitOptionMap()` | DB 已初始化 | 系统配置存储在数据库 options 表 |
| `model.GetPricing()` | DB 已初始化 | 加载模型价格数据 |
| `model.InitLogDB()` | 主 DB 或独立日志 DB | 日志写入可能使用独立数据库 |
| `common.InitRedisClient()` | Redis 可连接或未配置 | 初始化缓存和限流后端 |
| `i18n.Init()` | 本地语言文件 | 初始化后端国际化 |
| `oauth.LoadCustomProviders()` | DB 已初始化 | 自定义 OAuth 提供商从数据库加载 |
| `model.InitChannelCache()` | DB/Redis/内存缓存 | 渠道选择依赖渠道缓存 |
| `router.SetRouter()` | 前端 embed 资源、Gin | 注册 API、Relay、Web 静态资源路由 |

### 3. 前端与后端依赖关系

生产模式：

```text
web/default + web/classic
  -> Dockerfile 中用 Bun 构建 dist
  -> Go 编译阶段复制 dist
  -> main.go 使用 go:embed 编入二进制
  -> router/web-router.go 通过 static.Serve 提供静态资源
```

生产运行时关系：

- 前端不单独启动服务。
- 前端资源由后端 Gin 服务提供。
- 前端 API 请求直接访问同一 origin 下的 `/api`、`/v1` 等路径。
- `router/web-router.go` 会根据主题配置返回默认主题或 classic 主题资源。

开发模式：

```text
docker-compose.dev.yml 启动后端 + Redis + PostgreSQL
本地 web/default 使用 bun run dev 启动 Rsbuild dev server
前端 dev server 将 API 代理到 :3000
```

开发镜像 `Dockerfile.dev` 不构建真实前端，而是创建占位 `index.html`，目的是让 Go 的 `go:embed` 编译通过，实际页面由前端 dev server 提供。

## 五、开发部署机制

源码位置：`docker-compose.dev.yml`、`Dockerfile.dev`、`makefile`

开发 compose 服务：

| 服务 | 职能 |
| --- | --- |
| `new-api` | 从本地源码构建后端容器，暴露 `3000` |
| `redis` | 本地开发 Redis，无密码 |
| `postgres` | 本地开发 PostgreSQL，带 healthcheck |

开发启动方式：

```bash
docker compose -f docker-compose.dev.yml up -d
cd web/default
bun install
bun run dev
```

或使用 `makefile`：

| 命令 | 作用 |
| --- | --- |
| `make dev-api` | 启动后端、Redis、PostgreSQL 开发服务 |
| `make dev-api-rebuild` | 重新构建并启动后端开发容器 |
| `make dev-web` | 启动默认前端开发服务 |
| `make dev-web-classic` | 启动 classic 前端开发服务 |
| `make dev` | 启动 `dev-api` 和 `dev-web` |
| `make reset-setup` | 重置本地初始化向导状态和 root 用户 |

开发镜像特点：

- 只构建 Go 后端。
- 创建前端占位 dist，避免 `go:embed` 编译失败。
- 使用 `/data` 工作目录。
- 暴露 `3000`。

## 六、本机二进制与 systemd 部署

源码位置：`new-api.service`、`makefile`

除 Docker 外，项目也支持本机二进制部署。典型流程：

```text
构建前端 dist
  -> go build 生成 new-api 二进制
  -> 配置 .env 或系统环境变量
  -> 使用 systemd 托管进程
```

`new-api.service` 示例：

```ini
[Unit]
Description=One API Service
After=network.target

[Service]
User=ubuntu
WorkingDirectory=/path/to/new-api
ExecStart=/path/to/new-api/new-api --port 3000 --log-dir /path/to/new-api/logs
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

注意：

- `User`、`WorkingDirectory`、`ExecStart` 必须改成真实路径。
- 如果使用 SQLite，工作目录或 `SQLITE_PATH` 必须指向可写路径。
- 如果使用外部 MySQL/PostgreSQL/Redis，systemd 环境变量或 `.env` 必须配置连接字符串。

## 七、CI/CD 镜像与 Release 发布机制

源码位置：`.github/workflows/`

### 1. Docker 镜像发布

主要工作流：

| 文件 | 触发条件 | 产物 |
| --- | --- | --- |
| `docker-build.yml` | tag 或手动触发 | Docker Hub 多架构正式镜像 |
| `docker-image-alpha.yml` | `alpha` 分支或手动触发 | Docker Hub + GHCR alpha 镜像 |
| `docker-image-nightly.yml` | `nightly` 分支或手动触发 | Docker Hub nightly 镜像 |

核心流程：

```text
checkout
  -> 写入 VERSION
  -> docker buildx 构建 amd64/arm64
  -> 推送单架构镜像
  -> cosign 签名
  -> buildx imagetools create 合并多架构 manifest
```

正式镜像标签：

- `calciumion/new-api:<tag>-amd64`
- `calciumion/new-api:<tag>-arm64`
- `calciumion/new-api:<tag>`
- `calciumion/new-api:latest`

### 2. 二进制 Release

`release.yml` 会在正式 tag 上构建：

- Linux amd64。
- Linux arm64。
- macOS。
- Windows。

每个平台构建前都会先构建两个前端主题，然后再编译后端二进制。Release 会附带 checksum 文件。

## 八、数据库部署机制

### 1. 数据库选择

源码位置：`model/main.go`

数据库由 `SQL_DSN` 决定：

| 配置 | 使用数据库 |
| --- | --- |
| `SQL_DSN=postgresql://...` | PostgreSQL |
| `SQL_DSN=postgres://...` | PostgreSQL |
| `SQL_DSN=root:pass@tcp(...)/db` | MySQL |
| `SQL_DSN=local...` | SQLite |
| 不设置 `SQL_DSN` | SQLite |

默认 SQLite 路径：

```text
one-api.db?_busy_timeout=30000
```

可通过 `SQLITE_PATH` 覆盖。

### 2. 数据库迁移

`model.InitDB()` 会执行：

- 建立数据库连接。
- 设置连接池：
  - `SQL_MAX_IDLE_CONNS`，默认 100。
  - `SQL_MAX_OPEN_CONNS`，默认 1000。
  - `SQL_MAX_LIFETIME`，默认 60 秒。
- 主节点执行 GORM 自动迁移。
- MySQL 启动时检查中文字符集支持。
- PostgreSQL/MySQL/SQLite 分别处理关键字列名和布尔值差异。

注意：

- `NODE_TYPE=slave` 的节点不会执行主库迁移。
- 多机部署时应确保只有主节点执行迁移和部分后台任务。
- 日志数据库可以通过 `LOG_SQL_DSN` 单独配置；不配置时日志库复用主数据库。

## 九、Redis 与缓存部署机制

源码位置：`common/redis.go`、`main.go`、`model/user_cache.go`、`model/token_cache.go`、`model/channel_cache.go`

Redis 由 `REDIS_CONN_STRING` 启用：

| 状态 | 行为 |
| --- | --- |
| 未设置 `REDIS_CONN_STRING` | `RedisEnabled=false`，应用降级为无 Redis 模式 |
| 设置 Redis 连接串 | 解析 URL，创建客户端，5 秒内 ping 不通则启动失败 |

Redis 用途：

- Token 缓存。
- 用户缓存。
- 用户额度缓存。
- 渠道缓存配合内存缓存。
- 限流计数。
- 邮箱验证码限流。
- 模型请求限流。
- 订阅与价格等 HybridCache。
- 多实例共享状态。

缓存相关配置：

| 环境变量 | 作用 |
| --- | --- |
| `REDIS_CONN_STRING` | Redis 连接字符串 |
| `REDIS_POOL_SIZE` | Redis 连接池大小，默认 10 |
| `SYNC_FREQUENCY` | 缓存同步和 Redis key 缓存秒数，默认 60 |
| `MEMORY_CACHE_ENABLED` | 启用内存缓存 |
| `CHANNEL_UPDATE_FREQUENCY` | 自动更新渠道频率 |
| `BATCH_UPDATE_ENABLED` | 启用批量更新 |
| `BATCH_UPDATE_INTERVAL` | 批量更新间隔，默认 5 秒 |

源码中有一个重要逻辑：

```text
if RedisEnabled {
    MemoryCacheEnabled = true
}
```

也就是说 Redis 启用后会强制开启内存缓存兼容模式。

## 十、多节点部署机制

多节点部署时，多个 `new-api` 实例共享同一数据库和 Redis。

推荐关系：

```text
负载均衡/Nginx
  -> new-api node 1
  -> new-api node 2
  -> new-api node N
所有 new-api 节点
  -> 同一个 PostgreSQL/MySQL
  -> 同一个 Redis
```

关键环境变量：

| 环境变量 | 作用 |
| --- | --- |
| `SESSION_SECRET` | 多节点必须一致，否则 Cookie Session 无法互认 |
| `CRYPTO_SECRET` | 使用共享 Redis 时必须一致，否则加密数据无法解密 |
| `NODE_TYPE=master/slave` | 控制是否执行迁移和部分主节点任务 |
| `NODE_NAME` | 标识节点名称，写入审计日志 |
| `REDIS_CONN_STRING` | 多节点共享缓存与限流 |
| `SQL_DSN` | 多节点共享数据库 |

主从节点差异：

| 节点类型 | 行为 |
| --- | --- |
| master，默认 | 执行数据库迁移、日志库迁移、任务批量更新、部分后台任务 |
| slave | 跳过数据库迁移和部分主节点任务，适合作为横向扩展节点 |

注意：

- 不设置 `NODE_TYPE` 时，源码默认 `IsMasterNode = true`。
- 多实例部署如果所有节点都用默认 master，可能导致重复任务和迁移竞争。
- Session 密钥必须固定，不能使用每次启动随机生成的默认值。

## 十一、关键环境变量与注意事项

### 1. 必须修改默认密码

`docker-compose.yml` 中示例密码均为 `123456`：

- PostgreSQL root 密码。
- Redis requirepass。
- 可选 MySQL root 密码。

生产部署必须修改，否则数据库和缓存存在严重安全风险。

### 2. `SESSION_SECRET` 不能使用默认示例值

源码位置：`common/init.go`

如果设置为：

```text
SESSION_SECRET=random_string
```

应用会直接打印警告并终止启动。

如果完全不设置 `SESSION_SECRET`：

- 单节点会使用启动时随机生成的值。
- 容器重启后旧 Cookie 可能失效。
- 多节点之间登录态无法共享。

因此生产环境建议显式设置足够随机且稳定的 `SESSION_SECRET`。

### 3. 使用 Redis 时应设置 `CRYPTO_SECRET`

如果未设置 `CRYPTO_SECRET`，源码会使用 `SESSION_SECRET` 作为加密密钥。

多节点或共享 Redis 场景应显式设置一致的 `CRYPTO_SECRET`，否则不同节点可能无法解密共享数据。

### 4. 持久化目录必须保留

Docker 部署时：

```text
./data:/data
./logs:/app/logs
pg_data:/var/lib/postgresql/data
```

作用：

- `/data` 保存 SQLite 数据库和应用运行数据。
- `/app/logs` 保存应用日志。
- `pg_data` 保存 PostgreSQL 数据。

升级或重建容器时不要删除这些卷，除非明确要清空数据。

### 5. 数据库 ready 问题

生产 compose 的 `depends_on` 不等待 PostgreSQL 真正可用。第一次启动时如果数据库启动较慢，`new-api` 可能连接失败并重启。

处理方式：

- 保留 `restart: always`。
- 或参考开发 compose 为 PostgreSQL 添加 healthcheck 和 `condition: service_healthy`。
- 观察 `docker logs new-api` 确认迁移成功。

### 6. SQLite 适合轻量部署，不适合高并发多实例

未设置 `SQL_DSN` 时会使用 SQLite。SQLite 简化部署，但：

- 不适合多节点共享。
- 高并发写入能力弱于 MySQL/PostgreSQL。
- Docker 必须挂载 `/data`，否则容器删除后数据库丢失。

生产或多人使用建议使用 PostgreSQL 或 MySQL。

### 7. PostgreSQL 与 MySQL 切换要同步修改 DSN 和依赖

切换数据库不只是改 `SQL_DSN`，还要同步：

- compose 中启用目标数据库服务。
- `depends_on` 指向目标数据库。
- volumes 中启用目标数据库的数据卷。
- 确认旧数据库数据是否需要迁移。

### 8. 端口和反向代理

应用默认监听 `3000`。

可通过两种方式修改：

- 命令参数：`--port 3000`。
- 环境变量：`PORT=3000`。

如果放到 Nginx/Caddy/负载均衡后面，需要确保：

- WebSocket 请求可转发。
- SSE/流式响应不要被代理缓冲破坏。
- 上传/请求体大小与 `MAX_REQUEST_BODY_MB`、代理 body limit 保持一致。
- 超时时间与 `STREAMING_TIMEOUT`、`RELAY_TIMEOUT` 协调。

### 9. 日志目录要可写

容器生产 compose 使用：

```text
command: --log-dir /app/logs
volumes:
  - ./logs:/app/logs
```

本机 systemd 部署时也需要保证 `--log-dir` 指向的目录存在且服务用户可写。

### 10. pprof 和调试能力不要随意暴露

相关环境变量：

- `ENABLE_PPROF=true` 会启动 `0.0.0.0:8005`。
- `DEBUG=true` 会输出更多日志。
- `PYROSCOPE_*` 会接入性能分析。

生产环境启用这些能力时应放在内网或加访问控制。

## 十二、推荐部署流程

### 1. 单机生产推荐

```text
1. 复制 docker-compose.yml
2. 修改 PostgreSQL、Redis 默认密码
3. 设置 SESSION_SECRET 和 CRYPTO_SECRET
4. 确认 SQL_DSN 和 REDIS_CONN_STRING 与密码一致
5. 挂载 ./data、./logs、pg_data
6. docker compose up -d
7. 查看 docker logs new-api
8. 访问 http://服务器IP:3000
9. 完成初始化向导或登录管理后台
```

### 2. 轻量单容器部署

适合测试或低负载：

```text
docker run
  -> 映射 3000
  -> 挂载 /data
  -> 不设置 SQL_DSN 时使用 SQLite
```

注意仍建议设置：

- `SESSION_SECRET`
- `TZ`
- 必要时设置 `SQLITE_PATH`

### 3. 多节点生产推荐

```text
1. 准备外部 PostgreSQL/MySQL
2. 准备外部 Redis
3. 所有节点使用同一 SQL_DSN
4. 所有节点使用同一 REDIS_CONN_STRING
5. 所有节点使用同一 SESSION_SECRET 和 CRYPTO_SECRET
6. 仅一个节点使用 NODE_TYPE=master
7. 其他节点设置 NODE_TYPE=slave
8. 每个节点设置不同 NODE_NAME
9. 前面接负载均衡
```

## 十三、整体部署关系图

生产 compose 默认关系：

```text
用户浏览器 / API 客户端
        |
        v
  http://host:3000
        |
        v
  new-api 容器
    |   |   |
    |   |   +--> 前端静态资源：Go embed + Gin static
    |   +------> Redis：缓存、限流、共享状态
    +----------> PostgreSQL：业务数据、配置、日志、任务
```

开发关系：

```text
浏览器
  -> web/default Bun dev server
       -> 代理 API 到 localhost:3000
            -> new-api-dev 容器
                 -> postgres-dev
                 -> redis-dev
```

多节点关系：

```text
客户端
  -> 负载均衡
       -> new-api node 1
       -> new-api node 2
       -> new-api node N

所有节点共享：
  -> PostgreSQL/MySQL
  -> Redis
  -> 相同 SESSION_SECRET / CRYPTO_SECRET
```

## 十四、结论

该项目的快速部署核心是 **容器化单体应用 + 可选外部依赖编排**：

- 前端不是单独部署服务，而是在镜像构建时打包并嵌入 Go 二进制。
- 运行时主服务只有 `new-api` 一个应用进程，对外提供所有 Web/API/Relay 能力。
- 数据库是强依赖，生产 compose 默认 PostgreSQL，也支持 MySQL 和 SQLite。
- Redis 是推荐依赖，主要提供缓存、限流和多实例共享状态；未配置时可降级运行。
- Docker Compose 是最完整的快速部署方式，单容器适合轻量场景，systemd 适合非 Docker 服务器。
- 多节点部署必须统一密钥、共享数据库和 Redis，并区分 master/slave 节点职责。
