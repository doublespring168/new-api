# 8-中间件

本文档基于当前项目源码中的 `main.go`、`router/`、`middleware/`、`controller/`、`service/`、`model/` 等模块整理，重点说明项目使用了哪些中间件、这些中间件提供了哪些能力，以及中间件之间如何通过 Gin Context、Session、Redis/内存缓存和业务服务形成请求处理链路。

## 一、中间件总体分层

项目的中间件可以按职责分为 9 类：

| 分类 | 主要中间件 | 核心能力 |
| --- | --- | --- |
| 全局基础能力 | `gin.CustomRecovery`、`RequestId`、`PoweredBy`、`I18n`、`SetUpLogger`、`sessions.Sessions` | 异常兜底、请求追踪、版本响应头、语言识别、访问日志、Cookie Session |
| Web 静态资源 | `gzip.Gzip`、`GlobalWebRateLimit`、`Cache`、`static.Serve` | 前端资源压缩、Web 限流、静态资源缓存、主题资源服务 |
| 管理 API | `RouteTag("api")`、`gzip.Gzip`、`BodyStorageCleanup`、`GlobalAPIRateLimit` | API 标记、响应压缩、请求体临时存储清理、管理接口全局限流 |
| 身份认证 | `UserAuth`、`AdminAuth`、`RootAuth`、`TryUserAuth`、`TokenAuth`、`TokenAuthReadOnly`、`TokenOrUserAuth` | Dashboard 用户认证、角色鉴权、API Token 认证、只读 Token 查询、Session/Token 双模式认证 |
| 安全校验 | `TurnstileCheck`、`SecureVerificationRequired`、`OptionalSecureVerification`、`DisableCache` | 人机校验、敏感操作二次验证、防敏感数据缓存 |
| 限流控制 | `GlobalWebRateLimit`、`GlobalAPIRateLimit`、`CriticalRateLimit`、`SearchRateLimit`、`EmailVerificationRateLimit`、`ModelRequestRateLimit` | IP 限流、用户维度限流、邮箱验证码限流、模型请求总量/成功量限流 |
| Relay 分发 | `CORS`、`DecompressRequestMiddleware`、`StatsMiddleware`、`SystemPerformanceCheck`、`Distribute` | 跨域、请求解压、连接统计、系统负载保护、模型与渠道选择 |
| 协议适配 | `KlingRequestConvert`、`JimengRequestConvert` | 将 Kling、即梦等供应商格式转换为项目统一视频生成接口 |
| 辅助治理 | `BodyStorageCleanup`、`Cache`、`DisableCache`、`RouteTag`、`RelayPanicRecover` | 临时资源清理、缓存策略、日志路由标签、Relay panic 兜底 |

## 二、主要挂载位置

### 1. 全局 Gin Engine 链路

`main.go` 中对整个 `gin.Engine` 挂载了基础中间件：

| 挂载顺序 | 中间件 | 作用 |
| --- | --- | --- |
| 1 | `gin.CustomRecovery(...)` | 捕获全局 panic，记录错误并返回 OpenAI 风格错误 JSON，避免服务进程因请求异常崩溃 |
| 2 | `middleware.RequestId()` | 为每个请求生成 `X-Oneapi-Request-Id`，同时写入 Gin Context 和标准 request context |
| 3 | `middleware.PoweredBy()` | 写入 `X-New-Api-Version` 响应头 |
| 4 | `middleware.I18n()` | 根据用户设置、`Accept-Language` 或默认语言决定当前请求语言 |
| 5 | `middleware.SetUpLogger(server)` | 使用自定义 Gin Logger，输出状态码、延迟、IP、方法、路径、路由标签、请求 ID |
| 6 | `sessions.Sessions("session", cookie.NewStore(...))` | 提供 Cookie Session，供登录态、角色、Turnstile、安全验证等功能使用 |

全局链路解决的是所有入口共享的问题：异常兜底、可观测性、语言、会话和版本标识。

### 2. Web 前端链路

`router/web-router.go` 为前端静态资源挂载：

| 中间件 | 作用 |
| --- | --- |
| `gzip.Gzip(gzip.DefaultCompression)` | 对前端静态资源响应进行 gzip 压缩 |
| `GlobalWebRateLimit()` | 对 Web 请求按客户端 IP 做全局限流 |
| `Cache()` | 首页不缓存，静态资源缓存 7 天，并写入缓存版本头 |
| `static.Serve("/", themeFS)` | 使用 `gin-contrib/static` 提供主题感知的前端构建产物访问 |
| `NoRoute` 内设置 `RouteTagKey=web` | 未命中路由时按 Web SPA 回退返回前端 `index.html`，同时为日志打上 `web` 标签 |

### 3. 管理 API 链路

`router/api-router.go` 的 `/api` 路由组挂载：

| 中间件 | 作用 |
| --- | --- |
| `RouteTag("api")` | 设置日志路由标签为 `api` |
| `gzip.Gzip(gzip.DefaultCompression)` | 压缩 API 响应 |
| `BodyStorageCleanup()` | 请求结束后清理可复用请求体和文件源缓存 |
| `GlobalAPIRateLimit()` | 对管理 API 按 IP 做全局限流 |

在具体接口上再按需叠加 `UserAuth`、`AdminAuth`、`RootAuth`、`CriticalRateLimit`、`TurnstileCheck`、`SecureVerificationRequired`、`HeaderNavModuleAuth`、`TokenAuthReadOnly` 等中间件。

### 4. Relay API 链路

`router/relay-router.go` 在模型转发入口上挂载：

| 层级 | 中间件 | 作用 |
| --- | --- | --- |
| 根路由 | `CORS()` | 允许 API 客户端跨域访问 |
| 根路由 | `DecompressRequestMiddleware()` | 支持 gzip、br 请求体解压，并限制解压后请求体大小 |
| 根路由 | `BodyStorageCleanup()` | 清理请求体临时存储和文件源缓存 |
| 根路由 | `StatsMiddleware()` | 统计活跃连接数 |
| `/v1`、`/v1beta` 等 | `RouteTag("relay")` | 日志标记为 `relay` |
| Relay 核心组 | `SystemPerformanceCheck()` | CPU、内存、磁盘负载过高时拒绝请求 |
| Relay 核心组 | `TokenAuth()` | 验证 API Token、加载用户和 Token 上下文 |
| Relay 核心组 | `ModelRequestRateLimit()` | 按用户/分组限制模型请求数 |
| Relay 具体转发组 | `Distribute()` | 解析模型、选择渠道、写入渠道上下文，然后进入 controller/relay |

Relay 链路是项目最关键的中间件链。它不是单纯认证后转发，而是先完成协议兼容、Token 校验、分组选择、模型限流、渠道选择和上下文注入，再由后续 relay/controller 模块执行实际上游调用。

### 5. 视频接口链路

`router/video-router.go` 针对视频生成和视频任务查询使用几类链路：

| 路由类型 | 中间件 | 作用 |
| --- | --- | --- |
| `/v1/videos/:task_id/content` | `RouteTag("relay")`、`TokenOrUserAuth()` | 支持 Dashboard Session 或 API Token 查询视频内容 |
| `/v1/video...`、`/v1/videos...` | `RouteTag("relay")`、`TokenAuth()`、`Distribute()` | 标准 Token 认证后进入统一渠道分发 |
| `/kling/v1` | `RouteTag("relay")`、`KlingRequestConvert()`、`TokenAuth()`、`Distribute()` | 将 Kling 请求转换为统一视频生成请求再分发 |
| `/jimeng` | `RouteTag("relay")`、`JimengRequestConvert()`、`TokenAuth()`、`Distribute()` | 将即梦官方接口格式转换为统一视频生成/查询请求再分发 |

## 三、自研中间件能力清单

### 1. `RequestId`

源码位置：`middleware/request-id.go`

核心能力：

- 为每个请求生成请求 ID。
- 将请求 ID 写入响应头 `X-Oneapi-Request-Id`。
- 写入 Gin Context，供日志、错误响应、下游 relay 逻辑读取。
- 写入 Go 标准库 `context.Context`，便于跨函数调用追踪。
- 请求 ID 生成逻辑包含时间戳、构建路径哈希、随机片段等信息，减少冲突概率。

关联关系：

- `logger` 中间件会打印请求 ID。
- `abortWithOpenAiMessage` 会把请求 ID 附加到错误信息中。
- Relay 转发、控制器和服务层可以通过 context 获取请求 ID 做链路追踪。

### 2. `PoweredBy`

源码位置：`middleware/request-id.go`

核心能力：

- 写入 `X-New-Api-Version` 响应头。
- 让客户端、反向代理或排障人员可以识别当前服务版本。

### 3. `I18n`

源码位置：`middleware/i18n.go`

核心能力：

- 识别当前请求语言。
- 优先读取请求上下文中的用户设置语言。
- 其次解析 `Accept-Language`。
- 最后回退到后端 i18n 默认语言。
- 将语言写入 Gin Context，供 `common.TranslateMessage`、`i18n.T` 等翻译函数使用。

注意点：

- `I18n` 是全局早期中间件，通常早于用户认证执行，因此大多数未认证请求主要依赖 `Accept-Language` 或默认语言。
- Token 认证后会把用户设置写入 context，后续业务逻辑可继续使用用户级语言信息。

### 4. `SetUpLogger` 与 `RouteTag`

源码位置：`middleware/logger.go`

核心能力：

- 基于 `gin.LoggerWithFormatter` 自定义访问日志格式。
- 输出时间、路由标签、请求 ID、HTTP 状态、耗时、客户端 IP、方法、路径。
- `RouteTag(tag)` 将 `route_tag` 写入 Gin Context。
- 当前主要标签包括：
  - `api`：管理 API。
  - `relay`：模型转发/API 兼容入口。
  - `old_api`：旧 dashboard API。
  - `web`：前端静态资源或 SPA fallback。

关联关系：

- `RouteTag` 本身不做业务判断，主要为日志、监控、排障提供分类维度。

### 5. `BodyStorageCleanup`

源码位置：`middleware/body_cleanup.go`

核心能力：

- 在请求处理完成后执行清理。
- 调用 `common.CleanupBodyStorage(c)` 清理可复用请求体临时存储。
- 调用 `service.CleanupFileSources(c)` 清理 relay 文件源、图片源、上传源等临时缓存。

关联关系：

- `Distribute`、`KlingRequestConvert`、`JimengRequestConvert`、relay 转换逻辑会读取或复用请求体。
- 该中间件确保大请求、文件、多模态输入处理后不会长期占用内存或磁盘临时资源。

### 6. `Cache`

源码位置：`middleware/cache.go`

核心能力：

- 对 Web 静态资源设置缓存策略。
- 首页 `/` 使用 `no-cache`，保证前端入口页可以及时更新。
- 非首页静态资源使用较长缓存时间，当前为 `max-age=604800`。
- 写入缓存版本头，便于前端资源版本治理。

适用位置：

- 仅挂载在 Web 前端静态资源链路。

### 7. `DisableCache`

源码位置：`middleware/disable-cache.go`

核心能力：

- 对敏感接口设置强禁用缓存响应头：
  - `Cache-Control: no-store, no-cache, must-revalidate, private, max-age=0`
  - `Pragma: no-cache`
  - `Expires: 0`
- 避免浏览器、代理或网关缓存敏感数据。

典型场景：

- 获取渠道密钥。
- 获取 Token 密钥。
- 批量查看 Token key。
- 与 `CriticalRateLimit`、`SecureVerificationRequired` 组合保护高敏操作。

### 8. `CORS`

源码位置：`middleware/cors.go`

核心能力：

- 基于 `gin-contrib/cors` 提供跨域能力。
- 允许常见方法：`GET`、`POST`、`PUT`、`DELETE`、`OPTIONS`。
- 允许请求头 `*`。
- Relay、旧 API、Token 查询类接口会使用该能力，以兼容浏览器端或第三方客户端调用。

注意点：

- 该项目的 CORS 配置偏开放，安全边界主要依赖 Token、Session、角色、限流和业务校验。

### 9. `DecompressRequestMiddleware`

源码位置：`middleware/gzip.go`

核心能力：

- 处理非 GET 请求的压缩请求体。
- 支持 `Content-Encoding: gzip`。
- 支持 `Content-Encoding: br`，通过 `andybalholm/brotli` 解压。
- 解压后删除 `Content-Encoding`，避免后续逻辑重复处理。
- 对解压后的 body 使用 `http.MaxBytesReader` 限制最大体积。
- 未压缩请求也会包一层大小限制。

关联关系：

- Relay 请求经常包含大 JSON、多模态输入或文件引用，该中间件用于兼容客户端压缩提交，同时防止解压炸弹和超大请求体。

### 10. `StatsMiddleware`

源码位置：`middleware/stats.go`

核心能力：

- 使用原子计数统计当前活跃连接数。
- 请求进入时计数加一，请求结束后计数减一。
- `GetStats` 供控制器或监控接口读取。

适用位置：

- 挂载在 Relay 根路由，用于观察模型转发入口并发情况。

### 11. `SystemPerformanceCheck`

源码位置：`middleware/performance.go`

核心能力：

- 检查系统性能监控配置是否启用。
- 根据 CPU、内存、磁盘等阈值判断当前系统是否过载。
- 过载时提前拒绝模型请求，保护服务稳定性。
- 对 Anthropic `/v1/messages` 风格接口返回 Claude 兼容错误格式。
- 对其他接口返回 OpenAI 风格错误格式。

关联关系：

- 挂载在 Relay 和 Playground 模型请求链路，位于认证和分发前。
- 这是系统级熔断/保护中间件，不依赖具体渠道是否可用。

### 12. `RelayPanicRecover`

源码位置：`middleware/recover.go`

核心能力：

- 捕获 Relay 链路 panic。
- 打印堆栈。
- 返回 OpenAI 风格错误响应。

当前使用情况：

- 源码中存在该中间件实现，但路由挂载中主要使用的是 `main.go` 的全局 `gin.CustomRecovery`。
- 可以视作 Relay 专用 panic 兜底实现，当前未作为主要路由链路显式挂载。

## 四、认证与鉴权中间件

### 1. `UserAuth`、`AdminAuth`、`RootAuth`

源码位置：`middleware/auth.go`

三者都基于 `authHelper`，区别是最低角色要求不同：

| 中间件 | 最低角色 | 典型场景 |
| --- | --- | --- |
| `UserAuth` | 普通用户 | 用户中心、订阅、日志、Token 管理、自助接口 |
| `AdminAuth` | 管理员 | 渠道、分组、模型、任务、兑换码、供应商管理 |
| `RootAuth` | Root 用户 | 系统配置、性能配置、自定义 OAuth、关键管理操作 |

核心能力：

- 优先读取 Cookie Session 中的 `username`、`role`、`id`、`status`。
- 如果没有 Session 用户名，则尝试用 `Authorization` 访问令牌调用 `model.ValidateAccessToken`。
- 要求请求头 `New-Api-User` 存在，并且与 Session/AccessToken 中的用户 ID 一致。
- 检查用户是否被禁用。
- 检查角色是否满足接口最低权限。
- 检查用户名和角色信息是否合法。
- 写入 `Auth-Version` 响应头，避免不同版本登录态混用。
- 写入 Gin Context：
  - `username`
  - `role`
  - `id`
  - `group`
  - `user_group`
  - `use_access_token`

关联关系：

- 管理 API 的大多数接口依赖这些 context 字段获取当前用户身份、角色和分组。
- `SearchRateLimit` 依赖 `UserAuth` 先写入 `id`。
- `HeaderNavModuleAuth` 和 `HeaderNavModulePublicOrUserAuth` 在需要登录时会内部调用 `UserAuth`。

### 2. `TryUserAuth`

源码位置：`middleware/auth.go`

核心能力：

- 尝试从 Session 中读取 `id`。
- 如果存在则写入 Gin Context。
- 不阻断未登录请求。

典型场景：

- 某些前端导航模块或公开页面允许匿名访问，但如果用户已登录则希望读取用户身份。

### 3. `TokenAuth`

源码位置：`middleware/auth.go`

核心能力：

- 解析多种客户端 Token 传递方式：
  - `Authorization: Bearer ...`
  - 直接 `Authorization` key。
  - `sk-` 前缀兼容处理。
  - WebSocket `Sec-WebSocket-Protocol` 中的 `openai-insecure-api-key`。
  - Anthropic `/v1/messages`、`/v1/models` 的 `x-api-key`。
  - Gemini 的 `key` query 参数或 `x-goog-api-key`。
  - Midjourney 的 `mj-api-secret`。
- 调用 `model.ValidateUserToken` 校验 Token。
- 校验 Token 状态、过期时间、剩余额度等核心约束。
- 校验 Token IP 白名单。
- 读取用户缓存，检查用户是否可用。
- 把用户设置、用户组、Token 组、Token 模型限制、Token 配额等写入 Gin Context。
- 支持 Token 组覆盖、用户可用组校验、废弃分组校验。
- 支持从 Token key 后缀指定渠道 ID，但仅管理员可使用。

主要写入的上下文：

| Context Key | 作用 |
| --- | --- |
| `id` | 当前用户 ID |
| `token_id` | 当前 Token ID |
| `token_key` | 当前 Token key |
| `token_name` | Token 名称 |
| `token_unlimited_quota` | Token 是否无限额度 |
| `token_quota` | Token 当前额度 |
| `ContextKeyTokenGroup` | Token 所属或覆盖分组 |
| `ContextKeyUsingGroup` | 本次请求实际使用分组 |
| `ContextKeyUserGroup` | 用户自身分组 |
| `ContextKeyTokenModelLimitEnabled` | Token 是否启用模型限制 |
| `ContextKeyTokenModelLimit` | Token 允许的模型集合 |
| `ContextKeyTokenCrossGroupRetry` | 是否允许跨组重试 |
| `ContextKeyTokenSpecificChannelId` | 指定渠道 ID |

关联关系：

- `ModelRequestRateLimit` 依赖 `id`、`ContextKeyTokenGroup`、`ContextKeyUserGroup`。
- `Distribute` 依赖 `ContextKeyUsingGroup`、Token 模型限制、指定渠道 ID。
- Relay 结算和日志模块依赖 `token_id`、`token_name`、Token 配额等信息。

### 4. `TokenAuthReadOnly`

源码位置：`middleware/auth.go`

核心能力：

- 用于只读查询接口。
- 只校验 Token key 是否存在。
- 不检查 Token 是否禁用、过期或额度不足。
- 仍然检查所属用户是否被禁用。
- 写入 `id`、`token_id`、`token_key`。

典型场景：

- 通过 API key 查询日志、用量等历史信息，即使 Token 已过期或额度耗尽，也允许读取自身相关数据。

### 5. `TokenOrUserAuth`

源码位置：`middleware/auth.go`

核心能力：

- 优先尝试 Dashboard Session 登录态。
- Session 有效时直接写入 `id` 并放行。
- Session 不可用时回退到 `TokenAuth`。

典型场景：

- 视频内容查询等既要支持 Web 控制台访问，也要支持 API 客户端访问的接口。

### 6. `HeaderNavModuleAuth` 与 `HeaderNavModulePublicOrUserAuth`

源码位置：`middleware/header_nav.go`

核心能力：

- 读取系统配置 `HeaderNavModules`。
- 支持按模块配置：
  - `enabled`：模块是否启用。
  - `requireAuth`：是否要求登录。
- `HeaderNavModuleAuth(module)`：
  - 模块禁用时返回 403。
  - 模块要求登录时调用 `UserAuth`。
  - 否则调用 `TryUserAuth`。
- `HeaderNavModulePublicOrUserAuth(module)`：
  - 模块禁用或要求登录时调用 `UserAuth`。
  - 否则匿名可访问，并用 `TryUserAuth` 尝试补充用户身份。

典型场景：

- 价格页、排行榜等可配置导航模块的访问控制。

## 五、限流类中间件

### 1. 通用 IP 限流

源码位置：`middleware/rate-limit.go`

涉及中间件：

- `GlobalWebRateLimit`
- `GlobalAPIRateLimit`
- `CriticalRateLimit`
- `DownloadRateLimit`
- `UploadRateLimit`

核心能力：

- 根据配置决定是否启用。
- Redis 可用时使用 Redis List 记录时间窗口内请求。
- Redis 不可用时使用 `common.InMemoryRateLimiter`。
- 限流 key 基于客户端 IP 和业务标记：
  - `GW`：Web。
  - `GA`：API。
  - `CT`：敏感接口。
  - `DW`：下载。
  - `UP`：上传。
- 超过窗口内请求数时返回 `429 Too Many Requests`。

典型场景：

- `GlobalWebRateLimit` 保护前端入口。
- `GlobalAPIRateLimit` 保护管理 API。
- `CriticalRateLimit` 保护登录、注册、重置密码、OAuth、支付、查看密钥等高风险操作。

### 2. `SearchRateLimit`

源码位置：`middleware/rate-limit.go`

核心能力：

- 面向搜索类接口的用户维度限流。
- 必须挂载在 `UserAuth` 之后。
- 限流 key 使用认证后的用户 ID，而不是客户端 IP。
- Redis 可用时使用 Redis List；否则使用内存限流器。

典型场景：

- 用户日志搜索接口 `/api/log/self/search`，避免单个用户高频查询拖慢系统。

### 3. `EmailVerificationRateLimit`

源码位置：`middleware/email-verification-rate-limit.go`

核心能力：

- 邮箱验证码发送限流。
- 默认 30 秒内最多 2 次。
- Redis 可用时使用 `INCR + TTL`。
- Redis 不可用时使用内存限流。
- 超限时返回等待秒数提示。

典型场景：

- `/api/verification` 邮箱验证码发送。

### 4. `ModelRequestRateLimit`

源码位置：`middleware/model-rate-limit.go`

核心能力：

- 面向模型请求的用户维度限流。
- 必须挂载在 `TokenAuth` 之后，因为依赖 `id`、Token 分组、用户分组。
- 支持两个维度：
  - 总请求数限制：包括失败请求。
  - 成功请求数限制：只在响应状态码小于 400 时记录。
- 支持分组级覆盖配置，通过 `setting.GetGroupRateLimit(group)` 获取。
- Redis 可用时：
  - 成功请求数使用 Redis List 时间窗口统计。
  - 总请求数使用 Redis 令牌桶限流器。
- Redis 不可用时使用内存限流器。

关联关系：

- 作用于 `/v1`、`/v1beta`、Gemini 兼容等 Relay 模型请求链路。
- 位于 `TokenAuth` 之后、`Distribute` 之前，在渠道选择前先进行请求频率治理。

## 六、安全校验类中间件

### 1. `TurnstileCheck`

源码位置：`middleware/turnstile-check.go`

核心能力：

- 集成 Cloudflare Turnstile 人机验证。
- 如果系统未启用 Turnstile，则直接放行。
- 如果 Session 中已有通过标记，则直接放行。
- 从 query 参数读取 `turnstile` token。
- 向 Cloudflare `siteverify` 提交 secret、response、remote IP。
- 验证成功后写入 Session 缓存，减少重复验证。

典型场景：

- 注册。
- 登录。
- 发送邮箱验证码。
- 重置密码。
- 用户签到。

### 2. `SecureVerificationRequired`

源码位置：`middleware/secure_verification.go`

核心能力：

- 对敏感操作要求二次安全验证。
- 检查用户是否已登录。
- 从 Session 中读取 `secure_verified_at`。
- 验证有效期为 300 秒。
- 未验证、格式错误、过期时分别返回业务错误码：
  - `VERIFICATION_REQUIRED`
  - `VERIFICATION_INVALID`
  - `VERIFICATION_EXPIRED`
- 过期或无效时清理 Session 中的验证状态。

典型场景：

- 查看渠道密钥等高敏接口。

### 3. `OptionalSecureVerification` 与 `ClearSecureVerification`

源码位置：`middleware/secure_verification.go`

核心能力：

- `OptionalSecureVerification` 不阻断请求，只把是否已安全验证写入 context：
  - `secure_verified`
  - `secure_verified_at`
- `ClearSecureVerification` 清理 Session 中的安全验证状态。

适用场景：

- 控制器需要根据是否验证展示不同字段，或者在敏感操作完成后清除验证状态。

## 七、Relay 分发中间件

### 1. `Distribute`

源码位置：`middleware/distributor.go`

`Distribute` 是项目 Relay 链路最核心的业务中间件。它同时承担模型解析、分组选择、渠道选择、渠道上下文注入和渠道亲和性记录等职责。

核心能力：

- 从不同协议请求中解析模型名：
  - OpenAI JSON body。
  - form/multipart body。
  - Midjourney 路径和请求体。
  - Suno 请求。
  - Gemini 路径。
  - Realtime query。
  - moderation、embeddings、images、audio 等特殊接口。
  - Playground 请求。
  - 视频生成/查询请求。
- 检查 Token 模型限制：
  - 如果 Token 启用了模型白名单，请求模型必须在允许集合内。
  - 使用 `ratio_setting.FormatMatchingModelName` 做模型匹配名称归一。
- 处理 Playground 分组覆盖：
  - Playground 请求可以带 `group`。
  - 需要校验目标分组是否在用户可用分组内。
- 处理指定渠道：
  - 如果 `TokenAuth` 从 Token key 中解析到了管理员指定渠道 ID，则直接加载该渠道。
  - 校验渠道存在且启用。
- 处理渠道亲和性：
  - 通过 `service.GetPreferredChannelByAffinity` 获取偏好渠道。
  - 偏好渠道可用时优先使用。
  - 支持 auto 分组下从用户自动分组中寻找可用渠道。
  - 按配置决定亲和渠道失败后是否跳过重试。
- 常规渠道选择：
  - 调用 `service.CacheGetRandomSatisfiedChannel`。
  - 根据模型、分组、重试参数从渠道缓存中选择满足条件的渠道。
  - 找不到渠道时返回 OpenAI 风格错误，错误码可标识为模型不可用。
- 写入请求开始时间：
  - `ContextKeyRequestStartTime`。
- 调用 `SetupContextForSelectedChannel` 注入渠道上下文。
- 请求成功后记录渠道亲和性：
  - 响应状态码小于 400 时调用 `service.RecordChannelAffinity`。

### 2. `SetupContextForSelectedChannel`

源码位置：`middleware/distributor.go`

核心能力：

- 将选中的渠道完整写入 Gin Context，供 relay/controller/service 后续使用。
- 写入原始模型名、渠道 ID、渠道名、渠道类型、创建时间、渠道设置等。
- 写入渠道密钥、基础 URL、组织 ID、区域、API version、插件、bot id 等供应商字段。
- 写入模型映射、状态码映射、自动禁用配置。
- 写入 header/param 覆盖配置。
- 合并渠道亲和性模板中的请求覆盖配置。
- 支持多 key 渠道，写入当前使用的 key index 和 key 信息。
- 默认设置系统提示词覆盖开关为 false。

主要上下文能力：

| 上下文内容 | 后续使用方 |
| --- | --- |
| 渠道类型、渠道 ID、渠道名 | relay 适配器、日志、结算、自动禁用 |
| Base URL、API Key、组织 ID、区域 | 供应商 HTTP 客户端 |
| 模型映射 | 请求转换和供应商模型名映射 |
| 状态码映射 | 上游错误归一化 |
| 自动禁用 | 失败处理、渠道治理 |
| Header/Param 覆盖 | 供应商请求构造 |
| 多 key 信息 | 渠道 key 轮换和重试 |

### 3. `abortWithOpenAiMessage` 与 `abortWithMidjourneyMessage`

源码位置：`middleware/utils.go`

核心能力：

- 统一中间件层错误响应。
- `abortWithOpenAiMessage` 返回 OpenAI 风格错误结构。
- 错误信息会追加请求 ID，方便用户报错时定位日志。
- 记录错误日志，并尽量带上用户 ID。
- `abortWithMidjourneyMessage` 返回 Midjourney 兼容错误结构。

关联关系：

- `TokenAuth`、`Distribute`、`ModelRequestRateLimit`、`SystemPerformanceCheck` 等中间件在失败时大量使用这些工具函数保持响应格式一致。

## 八、协议转换中间件

### 1. `KlingRequestConvert`

源码位置：`middleware/kling_adapter.go`

核心能力：

- 读取 Kling 请求体。
- 支持从 `model_name` 或 `model` 字段识别模型。
- 转换为项目统一视频生成请求结构：
  - `model`
  - `prompt`
  - `metadata`
- 重写请求 body。
- 重写请求路径为 `/v1/video/generations`。
- 将转换后的请求体写入 `common.KeyRequestBody`，便于后续复用。
- 如果没有 `image`，设置任务动作为文本生成。

关联关系：

- 转换后继续执行 `TokenAuth` 和 `Distribute`，因此后续链路可以按统一视频接口处理 Kling 请求。

### 2. `JimengRequestConvert`

源码位置：`middleware/jimeng_adapter.go`

核心能力：

- 要求 query 中存在 `Action`。
- 从请求体中读取 `req_key` 作为模型名。
- 读取 `prompt` 并构建统一视频请求。
- 重写请求 body。
- 生成类请求重写路径为 `/v1/video/generations`。
- 查询类 `CVSync2AsyncGetResult`：
  - 要求 `task_id`。
  - 重写路径为 `/v1/video/generations/{task_id}`。
  - 将请求方法改为 `GET`。
  - 写入 `task_id`。
  - 设置 `relay_mode=VideoFetchByID`。

关联关系：

- 该中间件把即梦官方接口的 Action 风格请求转换为项目内部统一视频接口，使后续 Token、分发、relay 逻辑不需要为即梦单独维护完整入口链。

## 十、中间件之间的关键依赖关系

### 1. 管理 API 依赖关系

典型链路：

```text
全局 Recovery
  -> RequestId
  -> PoweredBy
  -> I18n
  -> Logger
  -> Session
  -> RouteTag(api)
  -> gzip
  -> BodyStorageCleanup
  -> GlobalAPIRateLimit
  -> UserAuth/AdminAuth/RootAuth
  -> CriticalRateLimit/Turnstile/SecureVerification 等
  -> Controller
```

关键依赖：

- `UserAuth/AdminAuth/RootAuth` 依赖 `sessions.Sessions`。
- `CriticalRateLimit` 可以独立工作，通常放在敏感接口上。
- `SearchRateLimit` 必须放在 `UserAuth` 之后，因为它需要 `id`。
- `SecureVerificationRequired` 依赖登录态和 Session。
- `DisableCache` 通常和返回敏感字段的控制器配合。

### 2. Relay 请求依赖关系

典型链路：

```text
全局 Recovery
  -> RequestId
  -> PoweredBy
  -> I18n
  -> Logger
  -> Session
  -> CORS
  -> DecompressRequestMiddleware
  -> BodyStorageCleanup
  -> StatsMiddleware
  -> RouteTag(relay)
  -> SystemPerformanceCheck
  -> TokenAuth
  -> ModelRequestRateLimit
  -> Distribute
  -> Relay Controller
  -> Provider Adapter
```

关键依赖：

- `TokenAuth` 必须早于 `ModelRequestRateLimit`，因为后者需要用户 ID 和分组。
- `TokenAuth` 必须早于 `Distribute`，因为 `Distribute` 需要 Token 模型限制、使用分组、指定渠道 ID。
- `DecompressRequestMiddleware` 必须早于读取请求体的分发/转换逻辑。
- `BodyStorageCleanup` 必须覆盖读取请求体的链路，确保请求结束后释放临时资源。
- `SystemPerformanceCheck` 放在渠道选择前，系统过载时可以尽早拒绝请求。

### 3. 视频适配链路依赖关系

典型链路：

```text
Kling/Jimeng 原始请求
  -> KlingRequestConvert/JimengRequestConvert
  -> TokenAuth
  -> Distribute
  -> Video Relay Controller
```

关键依赖：

- 协议转换必须早于 `Distribute`，否则分发中间件无法按统一格式解析模型。
- 协议转换也早于 `TokenAuth`，因为转换可能重写 path/body，使后续认证和分发处于统一入口语义下。

## 十二、设计特点与注意事项

1. 中间件承担了大量业务编排职责  
   该项目的中间件不是只做通用 HTTP 处理。尤其是 `TokenAuth` 和 `Distribute`，它们把用户、Token、分组、模型、渠道、供应商参数等核心业务上下文准备好，后续 controller/relay 主要基于这些 context 执行转换、请求和结算。

2. Relay 链路高度依赖中间件顺序  
   `DecompressRequestMiddleware -> TokenAuth -> ModelRequestRateLimit -> Distribute` 的顺序很关键。顺序错误会导致请求体无法复用、限流缺少用户信息、渠道选择缺少分组或模型限制。

3. Redis 与内存限流都有降级实现  
   通用限流、邮箱验证码限流、模型请求限流均支持 Redis 和内存模式。Redis 适合多实例部署；内存模式适合单实例或开发环境。

4. 错误响应兼容多个上游协议  
   中间件层会根据接口类型返回 OpenAI、Claude、Midjourney 等不同风格错误，保证客户端兼容性。

5. Session 与 Token 是两套认证体系  
   管理端主要使用 Cookie Session 和访问令牌；Relay 主要使用 API Token。`TokenOrUserAuth` 是少数支持两者同时访问的桥接中间件。

6. 配置控制能力较强  
   Turnstile、全局限流、搜索限流、模型限流、HeaderNav 模块、安全验证、性能保护等都受配置影响，中间件运行结果会随系统配置动态变化。

7. 请求体复用和清理是 Relay 的基础设施  
   多个中间件和 relay 转换器会读取请求体。项目通过 body storage 机制保证请求体可重复读取，再通过 `BodyStorageCleanup` 做统一清理。
